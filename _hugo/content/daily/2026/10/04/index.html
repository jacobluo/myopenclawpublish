总览

企业 Agent 评测必须看最终状态

Microsoft 与 Hugging Face 发布 ThinkingBox，核心观点是 tool call 成功不等于任务完成。一个 agent 可以正确调用订单、物流、客户、工单和政策工具，却仍然把业务对象留在错误状态，或给用户一个没有解决问题的结论。

Stateful workflow 成为 eval 主战场

ThinkingBox 用隔离的 MCP tool session 执行 507 个有状态业务 workflow，并用终端后端状态和副作用评分。它把评测焦点从“模型会不会选工具”推进到“数据库、工单、账户状态、补偿动作是否符合真实流程”。

Agent 成本风险需要默认硬闸

Simon Willison 指出 coding agents 与 personal agents 会让人更容易生成和部署会花钱的代码。软提醒式预算不够，因为半夜的一封警告邮件可能来不及阻止数百到数千美元的额外消耗。

模型路由与预算控制正在会合

过去几天 LangChain model router、GitHub Copilot effort level 和今天的硬预算提醒共同指向同一个问题：agent 平台需要把质量、成本、延迟和风险放到统一控制面，而不是只靠更强模型。

今天不是发布大日，但信号密度高

本窗口内公开官方 feed 新增不多；OpenAI 与 GitHub 的 10 月 2 日内容已在昨天日报覆盖。今天值得保留的是两条基础设施级提醒：评测要落到真实状态，预算要能硬停止。

本期判断

Agent 从 demo 走向生产后，最危险的不是“看起来没做事”，而是“看起来做完了但系统状态错了”；最昂贵的也不是一次模型调用，而是低摩擦自动化把付费资源消耗放大。eval 和 budget cap 会成为 agent 平台的基本安全带。

核心主题

一、ThinkingBox：不要用工具调用成功来替代业务完成

Agent Evals / Enterprise WorkflowsHugging Face Blog / Microsoft · 2026-10-03 22:56 UTC · The Agent Said It Was Done. The Database Disagreed.

ThinkingBox 用一个客服场景说明问题：agent 连续完成多个看似正确的工具调用，能查订单、物流、用户资料、退款政策和工单状态，也能写入工单记录，但最终仍可能把工单错误地关闭为 resolved，或者没有真正回应用户的核心诉求。工具调用轨迹看起来很干净，后端状态却暴露任务没有完成。

这篇文章把评测目标从动作过程转向业务终局：ThinkingBox 在隔离的 MCP tool sessions 中运行 507 个有状态业务 workflow，每个 workflow 对多个 LLM agent 重复运行，并依据终端数据库状态、关键字段和副作用评分。重点不是让模型“讲清楚自己做了什么”，而是验证它是否把系统推进到应有状态。

它也给了一个很实用的评测分层：tool call validity 只能说明 agent 会不会调用工具；state transition 与 side effect 检查才更接近企业流程的真实可靠性。对客服、订单、财务、权限、合规等场景来说，错误状态比错误回答更危险，因为它会沉入系统记录并影响后续流程。

为什么值得看：Follow List 里的 eval、agent engineering、MCP、企业 workflow 和 AI product 线索都绕不开这个问题。多数 agent demo 仍停留在“调用了正确工具”或“输出看起来合理”，但生产系统需要证明数据库、工单、账户、审批和通知都落在正确状态。
后续行动：把内部 agent 的评测从 transcript review 扩展到状态断言；每类 workflow 设计 pre-state、expected terminal state、允许副作用和禁止副作用；优先为高风险流程建设可复现 sandbox，而不是只追加 prompt 约束。

二、默认硬预算上限：Agent 让“意外花钱”变得更容易

Agent Ops / Cost ControlSimon Willison · 2026-10-03 23:34 UTC · We’re going to need default hard budget caps on pretty much everything

Simon Willison 提醒，coding agents 和 personal agents 会显著降低生成代码、接入 API、部署服务和消耗云资源的摩擦。一段自动生成的服务如果连接了付费 API、托管平台、对象存储或云计算资源，软预算提醒往往不足以防止账单在无人值守时继续扩大。

他的主张是 pay-by-usage 服务应默认提供硬预算上限：到达阈值后直接停止服务或返回错误，而不是只发邮件提醒。对个人开发者、小团队和实验项目来说，宁愿服务报错，也比醒来发现多出一笔巨大账单更可接受。

这条提醒和前几天的模型路由、Copilot review effort、GitHub token 迁移都在同一条线上：agent 平台不只是要“能执行”，还要有明确的成本边界、权限边界和失败边界。随着 agent 自动生成和启动更多后台任务，预算 cap 将从财务功能变成安全功能。

为什么值得看：AI agent 正在把一次性提示变成持续运行的软件行为。没有硬预算、配额、超时、并发限制和资源隔离，agent 的小错误会被自动化放大成真实账单或生产事故。
后续行动：检查所有 agent/coding workflow 使用的 OpenAI、云厂商、数据库、爬虫、邮件、向量库和托管平台是否有硬上限；默认开启月度/日度 budget cap；对自动部署和后台任务设置 TTL、最大并发、最大重试和人工审批阈值。
