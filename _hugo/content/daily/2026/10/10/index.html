核心主题

一、OpenAI / Asana：浏览器 agent 从“会跑”进入“能算账”

OpenAI / Codex / Browser AgentOpenAI News RSS / Search Index · 2026-10-09 07:00 UTC · Asana cuts model costs 76x in browser tests with GPT-6.1 Sol

OpenAI RSS 显示，Asana 使用 GPT-6 Astra in Codex 优化 StackAI 的浏览器 agent 工作流，并在 GPT-6.1 Sol 上把估算模型成本降到原生产设置的 1/76，同时运行速度提升 5 倍。搜索索引披露的关键数字包括：144-run study、优化后平均约 0.47 美元模型成本、每次运行约 4 分钟，原生产设置在部分运行中至少约 36.21 美元且会撞到 step limit。

这个案例值得注意的不是“便宜模型替换贵模型”这么简单。Asana 让 GPT-6 Astra 在 Codex 中检查请求、用量记录和输出，提出并测试改进，再由团队通过 Command 审查结果、转为 tickets 和 PR，最后进入生产。这更像一条 agent-assisted performance engineering 流水线。

如果这些数字经正文复核成立，它说明浏览器 agent 的成本大头可能来自工作流结构：历史记录如何缓存、上下文如何追加、页面状态如何剪枝、失败重试如何设计。模型本身便宜是一部分，harness 与记录结构才是可以持续复利的地方。

为什么值得看：Follow List 重点关注 Codex、agent 与生产化。Asana 案例把 Codex 从“写代码”扩展成“让 agent 优化另一个 agent 的成本和速度”，这对企业内部自动化项目非常实用。
后续行动：复核 OpenAI 正文可访问版本，提取 144-run study 的方法；给内部浏览器自动化任务建立 cost/run、time/run、step limit、cache hit、retry rate、human review 的统一日志字段。

二、LangChain：模型路由应长在 harness 里

LangChain / Model RoutingLangChain Blog · RSS 2026-10-09 19:34 UTC（页面日期 2026-10-01） · How to Build a Model Router in the Harness

LangChain 把模型路由定义为 harness 级能力，而不是通用 LLM gateway 的薄层功能。文章称，其实验中 coding task 的中位成本相对 baseline 降低 64%，且没有明显质量下降；原因是大量任务不需要 frontier-level intelligence，只有少数任务值得升级到更强模型。

文章的关键判断是：路由决策需要看到任务类型、仓库上下文、工具状态、历史轨迹、失败成本和评测信号，而这些信息通常在 agent harness 中，而不是在模型网关里。一个只看 prompt 的网关很难知道当前调用是代码定位、规划、补丁生成、测试诊断还是最终审查。

这条线和 Asana、LegalOn 的 Codex 成本叙事互相印证。模型路由正在从“省钱技巧”变成 agent 架构的一层：观测、评测、路由、回退、审计需要一起设计。

为什么值得看：Agent 成本不是靠一次选型解决的，而是靠 harness 把任务拆清楚、记录清楚、评估清楚。对 OpenClaw/Codex 类系统，这直接影响多模型、多 subagent 和长任务的成本边界。
后续行动：做一张“任务类型 - 推荐模型 - 升级条件 - 回退条件 - 成本字段”的路由表；优先覆盖代码搜索、计划、编辑、测试修复、报告撰写、网页抓取六类任务。

三、LangChain / Snyk：生产 agent 需要可感知的 UX 与客户化路径

LangChain / Production AgentsLangChain Blog · 2026-10-09 10:29 / 19:34 UTC · Managed Deep Agents Slack UX · Snyk Assist

Managed Deep Agents 的 Slack SDK 更新把 reactions 做成 API：agent 可以在 Slack 里用静态或动态 emoji 表达自己已看见、正在处理、发现问题或完成。看似小功能，其实是生产 UX 的基础件，因为用户需要低摩擦地判断 agent 是否进入了正确状态。

Snyk 案例则展示了另一条产品化路径：先把内部支持 agent 用于客户问题、知识库和排障流程，再逐步沉淀成面向客户的 Snyk Assist。LangChain、LangGraph 和 LangSmith 在这里分别承担编排、状态控制、观测与质量改进。

两条更新合起来看，生产 agent 的竞争点不只是推理能力，还包括渠道体验、用户反馈、内部支持数据、评测闭环和从 internal tool 到 external feature 的迁移能力。

为什么值得看：企业 agent 真正上线时，用户最先感知的是“它有没有收到、会不会乱动、结果能不能信”。Slack reactions、支持工单闭环和 LangSmith 轨迹比炫技 demo 更接近真实部署问题。
后续行动：为内部 IM agent 定义标准状态反应：收到、思考中、需要人工确认、执行中、失败、完成；同时把支持类 agent 的问题分类、引用来源、升级人工和满意度纳入 eval 数据。

四、Hugging Face / Ai2：GPU 集群调度从“排队”走向“预算 + 影响力”

Hugging Face / AI InfraHugging Face Blog / Ai2 · 2026-10-09 15:20 UTC · Impactful scheduling for GPU clusters

Ai2 在 Hugging Face 上发布 GPU cluster scheduling 文章，讨论如何在保持 full occupancy 的同时，把 GPU 时间分配给更高影响力的研究工作。文章把调度指标拆成 availability、occupancy、impact 等层级，并用仿真环境测试 preemption 与 GPU assignment 决策。

它批评了“高优先级免费且不可抢占”带来的 tragedy of the commons：如果 HIGH priority 没有成本，所有人都会占用它，最终系统无法区分真正高价值任务。Ai2 的方向是让每个 GPU 时间请求都消耗预算；无意义占坑会消耗团队额度，反而让诚实申请更大预算变成更理性的路径。

这篇不是模型发布，但和 agent 系统高度相关。无论是 GPU 训练、浏览器 agent、coding agent 还是多模型调用，资源治理都要从“谁先发起任务”转为“任务价值、预算、可抢占性和复现证据”。

为什么值得看：AI infra 的瓶颈不只是买更多 GPU，也包括把稀缺资源分配给更有价值的实验。对企业 agent 平台同样适用：预算和优先级必须是可执行的系统约束。
后续行动：把 GPU scheduler 的预算思路借到 agent 任务队列：每类自动化任务设置预算、优先级、可中断性、人工批准阈值和“占坑成本”。
