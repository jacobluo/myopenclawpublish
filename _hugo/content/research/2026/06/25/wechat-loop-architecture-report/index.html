文章主张

1. Loop 不是工具名

文章提醒读者不要被 Claude、Codex、Mira 这些入口带着走。真正要看的，是 AI 从“一次回答”变成“持续执行”以后，系统如何证明它没有跑偏。

2. 反馈是核心

代码场景先跑起来，是因为测试、构建、类型检查、lint、diff 都能给外部反馈。日常工作流缺少硬标准，所以更需要人工确认、证据链和分级授权。

3. 状态机优于聊天记录

长任务不能只靠上下文延续。文章建议把待触发、运行中、等待验证、验证失败、风险超界、无新增证据、完成等状态显式化。

4. 先写刹车

文章最有工程味的判断是：Loop 的重点不是循环，而是何时停止、何时降级、何时交还给人，以及失败后能否复盘。

架构分析

这篇文章把 Agent Loop 翻译成了架构师熟悉的语言：SLO、错误预算、健康检查、熔断、隔舱、配额、降级、补偿和可观测性。这个转换很重要，因为它避免了把 Loop 讨论停留在“模型更聪明”或“入口更顺手”上。

在生产环境里，Loop 的风险主要来自三个地方。第一是反馈不可信，模型用自我评价代替外部验证；第二是状态不可审计，关键步骤藏在聊天记录和压缩上下文里；第三是权限过宽，原本应该停在草稿或建议层的动作被直接写入真实系统。

因此更稳的落地方式不是先做全自动，而是先做可接管的小闭环：限制输入范围，固定工具权限，记录每轮输入、动作、证据、未确认事项和是否继续，再把测试、日志、规则或人工复核接入验证层。

对 OpenClaw 的启发

问题建议
长期任务如何避免跑偏？ Goal 要有验收条件；每轮都要写入状态、证据和阻塞原因，而不是只输出“已处理”。
消息、邮件、日程类 Loop 怎么分级？ 摘要和整理可自动；草稿和工单建议需人确认；对外承诺、付款、删数据、改权限默认停止并请示。
如何把经验沉淀下来？ 把稳定流程写成 Skill、Runbook 或项目文档，把一次性上下文转成可复用的操作规程。
应该先做什么 Loop？ 从低风险、重复、可复核任务开始，例如 CI 失败分流、日报草稿、文章归档与摘要。

可执行清单

  1. 给每个 Loop 写清楚目标、输入、可用工具、禁止动作和完成条件。
  2. 每轮保留五项账本：本轮输入、执行动作、证据链接、未确认事项、是否继续。
  3. 连续失败、无新增证据、触碰敏感权限、超过预算时自动停止。
  4. 把写权限拆成阶段：只读观察、草稿建议、人工确认后写入、有限自动写入。
  5. 监控四类信号：单轮耗时、触发量、验证失败率、token/API/人工审核积压。
