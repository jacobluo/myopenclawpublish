常驻 Agent：
不是一直思考，而是随时接得上工作

Anthropic《Building always-on agents》中文总结与工程解读：让模型从“等你提问”走向“有事件就工作”，真正要补的是模型外围的运行系统。

整理日期：2026-11-14原文作者：William Hu阅读约 7 分钟

先读结论

“始终在线”描述的是用户体验，不是模型持续运行的方式。原文中的 Agent 大部分时间休眠，事件到来才启动一轮工作，结束后保存必要信息，再等待下一次唤醒。

这不是发布了一个新模型，也不是只需开启某个开关就能无人值守。文章提供的是一套架构思路：在既有 Agent 工具调用循环外，补齐事件、时间、持久状态、授权和交付。

原文框架：五个部件各管一件事

1. 收件箱：什么事情值得启动工作

用户消息、Webhook 和后台结果先进入持久化事件列表，由 Worker 领取。原文建议同一收件箱只允许一个活跃 Worker，并合并连续事件，以免竞争、覆盖或重复回复。

2. 计时器：什么时候主动醒来

一次性跟进与周期任务分别保存；调度器到点后把事件写入收件箱，而不是直接调用模型。定时规则和待处理事件因此有清晰边界。

3. 记忆：下次醒来还知道什么

跨轮次保留用户指令、偏好、已发消息和任务进度。能在外部系统查到的信息，优先保存引用。会话压缩不能替代持久记忆，初始上下文则应保持精简。

4. 权限：能做什么，何时等人

工具动作需要区分自动执行、阻止和等待批准。原文讨论凭证代理与可延期的工具调用：暂停并保存会话，用户答复作为新事件到来后继续，不必一直占用 Worker。

5. 发件箱：结果如何到达用户

简单场景直接发送即可；需要发送节奏控制或错误恢复时，再建立独立发件箱和投递服务。一次工作也可以选择不发消息，并非每次唤醒都值得通知。

把它串起来：一轮工作如何结束，又如何继续

事件入箱 → Worker 领取 → 加载会话与记忆 → 在权限内执行 → 保存进度 → 按需通知 → 休眠

理解时要区分三个概念：任务是用户要完成的目标；会话是承载消息与工具记录的上下文；一轮运行是一次唤醒后的工作片段。同一个任务可以跨多轮运行，后续回复也可以回到原有会话。

因此，“等用户批准”不必是后台进程一直挂起等候。任务可以停在明确状态，释放执行资源；之后收到批准事件，再恢复必要上下文。连续性来自保存的状态，而不是同一个进程从不退出。

工程示例：每天生成一份资讯报告

以下为本文设计示例，并非官方示例代码

  1. 08:00 到点：调度器产生当天的报告事件，附上日期、时区和稳定的任务标识。
  2. 领取任务：Worker 检查是否已经完成，读取关注来源、上次检查时间和已发布记录。
  3. 采集与整理：抓取资料、去重并保留来源；抓取失败要记录覆盖缺口，不能写成“没有更新”。
  4. 形成可验收结果：生成报告，检查链接、日期、引用和页面；根据预先授权决定直接发布还是等待批准。
  5. 确认交付：保存发布地址和通知状态。发布成功但通知失败时，只补发通知，不再生成第二份报告。
  6. 休眠：下一次定时事件或用户追问到来，再读取必要进度继续。

与普通定时脚本相比，这套设计的价值不在“每天八点运行”本身，而在于它能够跨中断继续、接收补充要求，并把任务状态与消息投递状态分开管理。对于完全确定的工作流，脚本可能已经足够，不必每一步都调用模型。

最值得补充的一点：能重试，不等于不会重复操作

原文给出了持久化与去重方向，但不是完整的分布式事务方案。实际落地时，最容易出问题的是：外部动作已经成功，内部却还没来得及记录。

例如，Agent 已经发布报告，随后进程在写入“完成”状态前崩溃。重启后再次领取同一事件，可能重复发布。仅在收件箱中对事件去重，不能自动消除这种外部副作用。

本文建议的三个补强

  • 稳定标识：给“某日某类报告”这样的业务动作设置稳定 ID；支持幂等键的接口应复用该键。
  • 先核对再补做：请求超时或结果不确定时，先检查目标系统是否已经存在对应结果，而不是直接重发。
  • 分开记账：分别记录内容完成、发布确认、通知确认；每个阶段有自己的恢复路径。

“每箱一个 Worker”也需要执行层保证，例如带到期时间的租约及过期执行者约束，不能只靠提示词要求 Agent 不要并发。对于不支持幂等或查询核对的外部服务，无法轻率承诺端到端只执行一次。

成本与通知：不是醒得越频繁越主动

每次调用都要支付加载上下文、判断和工具调用的成本。把一个没有新信息的系统每分钟唤醒一次，通常只是在重复购买同一个判断。

  • 先用确定性代码筛选：去重、到期判断、是否有新增数据，不必都交给模型。
  • 按需加载记忆：优先读取任务摘要和索引，再获取相关明细，不把全部历史塞进每次调用。
  • 按价值通知：将真正需要用户行动的消息与普通完成回执区分；低优先级信息可以聚合。
  • 给失败设边界：配置重试次数、运行时限和升级处理条件，避免一个坏输入无限消耗预算。

原文还提到提示缓存与离线记忆整理。本文不复述其中的模型降本百分比：单一基准不能推导实际产品账单，真实成本还包含抓取、工具、失败重试与交付。

上线前，用六种故障验证它

本文建议的验收清单

  • 重复事件：同一个请求送两次，只形成一份业务结果。
  • 中途重启：Worker 消失后，任务仍然可见，且能够安全继续。
  • 结果不确定：外部接口超时后，能核对既有结果，而不是盲目重做。
  • 批准等待：任务停在正确阶段，其他任务仍能执行；答复回来后不丢前置条件。
  • 会话压缩：关键进度和用户约束仍能从持久存储恢复。
  • 投递失败：报告保留，通知可补发，不触发内容重复生产。

最小系统不一定需要五套独立服务：一个数据库可以存放不同逻辑表，一个应用也可以承担多种角色。应先明确状态和职责，再按负载拆分部署；不要把“架构上分开”误解为“必须上微服务”。

最后判断

这篇指南最有价值的地方，是把“更主动的 AI”从模型能力问题，转成一组可实现、可检查的系统职责。

模型决定这次怎么做；运行系统保证下次还能接上、失败可以恢复、权限没有越过、结果确实送达。定时器只是入口，可靠性才是长期使用的分水岭。
