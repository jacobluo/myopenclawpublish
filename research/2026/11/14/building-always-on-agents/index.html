常驻 Agent：
不是一直思考，而是随时接得上工作

Anthropic《Building always-on agents》中文总结与工程解读：让模型从“等你提问”走向“有事件就工作”，真正要补的是模型外围的运行系统。

整理日期：2026-11-14原文作者：William Hu更新：2026-11-15 · 新增 WorkBuddy 实践阅读约 12 分钟

先读结论

“始终在线”描述的是用户体验，不是模型持续运行的方式。原文中的 Agent 大部分时间休眠，事件到来才启动一轮工作，结束后保存必要信息，再等待下一次唤醒。

这不是发布了一个新模型，也不是只需开启某个开关就能无人值守。文章提供的是一套架构思路：在既有 Agent 工具调用循环外，补齐事件、时间、持久状态、授权和交付。

原文框架：五个部件各管一件事

1. 收件箱：什么事情值得启动工作

用户消息、Webhook 和后台结果先进入持久化事件列表，由 Worker 领取。原文建议同一收件箱只允许一个活跃 Worker，并合并连续事件，以免竞争、覆盖或重复回复。

2. 计时器：什么时候主动醒来

一次性跟进与周期任务分别保存；调度器到点后把事件写入收件箱，而不是直接调用模型。定时规则和待处理事件因此有清晰边界。

3. 记忆：下次醒来还知道什么

跨轮次保留用户指令、偏好、已发消息和任务进度。能在外部系统查到的信息，优先保存引用。会话压缩不能替代持久记忆，初始上下文则应保持精简。

4. 权限：能做什么，何时等人

工具动作需要区分自动执行、阻止和等待批准。原文讨论凭证代理与可延期的工具调用：暂停并保存会话，用户答复作为新事件到来后继续，不必一直占用 Worker。

5. 发件箱：结果如何到达用户

简单场景直接发送即可；需要发送节奏控制或错误恢复时，再建立独立发件箱和投递服务。一次工作也可以选择不发消息，并非每次唤醒都值得通知。

把它串起来：一轮工作如何结束，又如何继续

事件入箱 → Worker 领取 → 加载会话与记忆 → 在权限内执行 → 保存进度 → 按需通知 → 休眠

理解时要区分三个概念：任务是用户要完成的目标；会话是承载消息与工具记录的上下文；一轮运行是一次唤醒后的工作片段。同一个任务可以跨多轮运行，后续回复也可以回到原有会话。

因此，“等用户批准”不必是后台进程一直挂起等候。任务可以停在明确状态，释放执行资源；之后收到批准事件，再恢复必要上下文。连续性来自保存的状态，而不是同一个进程从不退出。

工程示例：每天生成一份资讯报告

以下为本文设计示例，并非官方示例代码

  1. 08:00 到点：调度器产生当天的报告事件，附上日期、时区和稳定的任务标识。
  2. 领取任务：Worker 检查是否已经完成，读取关注来源、上次检查时间和已发布记录。
  3. 采集与整理：抓取资料、去重并保留来源；抓取失败要记录覆盖缺口，不能写成“没有更新”。
  4. 形成可验收结果：生成报告，检查链接、日期、引用和页面；根据预先授权决定直接发布还是等待批准。
  5. 确认交付：保存发布地址和通知状态。发布成功但通知失败时，只补发通知，不再生成第二份报告。
  6. 休眠：下一次定时事件或用户追问到来，再读取必要进度继续。

与普通定时脚本相比，这套设计的价值不在“每天八点运行”本身，而在于它能够跨中断继续、接收补充要求，并把任务状态与消息投递状态分开管理。对于完全确定的工作流，脚本可能已经足够，不必每一步都调用模型。

最值得补充的一点：能重试，不等于不会重复操作

原文给出了持久化与去重方向，但不是完整的分布式事务方案。实际落地时，最容易出问题的是：外部动作已经成功，内部却还没来得及记录。

例如，Agent 已经发布报告，随后进程在写入“完成”状态前崩溃。重启后再次领取同一事件，可能重复发布。仅在收件箱中对事件去重，不能自动消除这种外部副作用。

本文建议的三个补强

  • 稳定标识：给“某日某类报告”这样的业务动作设置稳定 ID；支持幂等键的接口应复用该键。
  • 先核对再补做：请求超时或结果不确定时，先检查目标系统是否已经存在对应结果，而不是直接重发。
  • 分开记账：分别记录内容完成、发布确认、通知确认；每个阶段有自己的恢复路径。

“每箱一个 Worker”也需要执行层保证，例如带到期时间的租约及过期执行者约束，不能只靠提示词要求 Agent 不要并发。对于不支持幂等或查询核对的外部服务，无法轻率承诺端到端只执行一次。

成本与通知：不是醒得越频繁越主动

每次调用都要支付加载上下文、判断和工具调用的成本。把一个没有新信息的系统每分钟唤醒一次，通常只是在重复购买同一个判断。

  • 先用确定性代码筛选：去重、到期判断、是否有新增数据，不必都交给模型。
  • 按需加载记忆：优先读取任务摘要和索引，再获取相关明细，不把全部历史塞进每次调用。
  • 按价值通知：将真正需要用户行动的消息与普通完成回执区分；低优先级信息可以聚合。
  • 给失败设边界：配置重试次数、运行时限和升级处理条件，避免一个坏输入无限消耗预算。

原文还提到提示缓存与离线记忆整理。本文不复述其中的模型降本百分比：单一基准不能推导实际产品账单，真实成本还包含抓取、工具、失败重试与交付。

上线前，用六种故障验证它

本文建议的验收清单

  • 重复事件：同一个请求送两次，只形成一份业务结果。
  • 中途重启：Worker 消失后，任务仍然可见，且能够安全继续。
  • 结果不确定：外部接口超时后，能核对既有结果，而不是盲目重做。
  • 批准等待：任务停在正确阶段，其他任务仍能执行；答复回来后不丢前置条件。
  • 会话压缩：关键进度和用户约束仍能从持久存储恢复。
  • 投递失败：报告保留，通知可补发，不触发内容重复生产。

最小系统不一定需要五套独立服务：一个数据库可以存放不同逻辑表，一个应用也可以承担多种角色。应先明确状态和职责，再按负载拆分部署；不要把“架构上分开”误解为“必须上微服务”。

WorkBuddy 实践：先跑通一个可恢复的日报助手

2026-11-15 补充 · 官方能力核对 + 本文实施建议

推荐起步方案：定时任务负责唤醒，WorkBuddy 负责采集与整理，工作空间负责保存进度，通知渠道负责交付。先做一个任务，再考虑外部事件驱动。以下是实践方案，并非已经完成的 WorkBuddy 环境配置或运行测试。

第一步：按数据位置选本地或云端

  • 本地任务：适合处理本机资料、操作本地项目。电脑与 WorkBuddy 客户端要保持运行；关机或退出可能中断或错过任务。
  • 云端任务：在云端沙箱执行，不依赖电脑在线。但不能读取本机文件路径；按当前官方文档，也不支持云端定时任务的内置企业微信推送。

下面的目录方案以本地任务为例。如果改用云端，要先验证可用连接器或服务的数据访问与持久化能力，不能把本地路径原样搬过去，也不能假设云端沙箱文件会永久保留。

第二步：建立独立工作空间

下面是自定义文件约定，不是 WorkBuddy 自动识别的特殊目录。应在任务提示词里明确要求读取与更新。

情报助手/
  rules.md          # 来源标准、输出要求、操作边界
  sources.md        # 关注清单
  state.json        # 已检查内容、报告与交付状态
  reports/          # 每日报告
  logs/             # 覆盖缺口与失败记录

WorkBuddy 内置记忆会定期从历史会话提取偏好等信息。它适合保存“用户喜欢怎样的报告”，但不应替代精确业务状态，例如“今天报告是否发布、通知是否确认成功”。后者放在显式状态文件中。

建议状态至少包含 task_id、checked_until、processed_urls、report_path、publish_status 和 notify_status。首期不发布时，将发布状态明确标为未启用。来源检查失败时，不要把该来源的检查水位当作成功推进。

第三步：创建每天 08:00 的任务

在「定时任务 → 新建」中指定上述工作空间，设置每日执行时间，并核对实际时区、模型和需要的连接器。先点击「立即运行」试跑，再开启周期执行。

可直接修改使用的任务提示词：

执行每日情报整理。先读取 rules.md、sources.md 和 state.json；首次运行时按约定初始化状态，其他必要文件缺失则说明缺失项，不猜测来源或规则。

检查上次成功检查以来的新增内容，按原始链接去重。重要结论附来源；抓取失败、无法核实及覆盖缺口单列。

将报告保存到 reports/YYYY-MM-DD.md，并记录本次进度。若当天报告已经完成，先检查已有产物，只在有明确新增内容时补充，不重复生产同一份报告。

只有对应动作确认成功后，才更新完成状态；失败时保留已完成步骤和下一步。首期只生成报告，不公开发布、不删除原始资料。

结果只输出：报告位置、五条以内高价值发现、需要处理的异常。若使用定时任务内置推送，不再调用其他工具向同一接收人重复通知。

边界：提示词描述的是行为目标，不是事务保证。并发、崩溃恢复与关键状态写入仍需要实际测试；涉及稳定业务运行时，应交由确定性程序管理。

第四步：权限与通知分别配置

先用默认权限试跑，观察哪些文件、命令、网络访问需要允许，再通过安全中心按实际需求细化规则。不要为了减少确认直接把所有任务切到完全访问；提示词里的“仅修改某目录”也不能替代权限限制。

本地定时任务的内置企微推送当前要求 WebSocket 长连接，URL 回调方式不适用于该推送入口。优先选择一种通知路径，避免内置推送与自建 MCP 同时发送。

飞书或其他系统可通过合适的 MCP／连接器评估接入，但应先验证实际工具、授权和发送能力。MCP 是工具接入方式，不自动提供可靠队列或发送去重。未拿到平台投递回执时，不要只根据任务完成就把通知标记为已送达。

第五步：确有需要时，补外部事件系统

固定周期汇总通常从一个定时任务就能起步；若需求变成“业务事件一到就处理”“多人同时派单”或“中断后可靠恢复”，建议再补持久队列与执行控制。

业务事件 → 持久队列 → 领取与锁定 → WorkBuddy 处理 → 记录结果 → 通知与补发

这是一种目标架构，不是已核实的 WorkBuddy 原生能力清单。外部系统如何触发 WorkBuddy，必须依据部署版本提供的可用接口另行验证；本文未确认通用的外部调用 API，因此不能把此箭头当作现成接口。

队列、锁、重试、状态转换和通知去重由脚本或服务承担。单机可以从 SQLite 开始；多进程领取必须用事务等机制保证，不能只让模型先读后写一个“运行中”字段。外部动作超时后，先核对是否已经成功，再决定重试。

最后：用三次试跑检查最小闭环

  1. 正常运行：能读取清单、形成带来源的报告，并保存明确状态。
  2. 同一天再运行：不会重复生成或重复通知；如有新增内容，行为符合补充规则。
  3. 中断后恢复：保留已有成果，只补未完成步骤；“发布成功、通知失败”不应导致再次发布。

这些是验收目标，不是内置保证。先连续运行几天，确认失败记录、质量与消耗符合预期，再逐步开启自动发布。若原有系统已经运行同类日报，新增 WorkBuddy 任务先保持测试状态，避免两个调度器同时生产和通知。

官方参考与核验边界

  • 定时任务：任务来源、创建入口、本地在线要求、云端限制与企微推送。
  • 记忆：偏好提取与记忆管理。
  • 默认权限与安全沙箱：工作空间、文件／命令／网络规则和工具管控。
  • MCP：外部工具与通知服务接入。

资料核对于 2026-11-14，实践章节补充于 2026-11-15。界面和功能可能随版本、灰度范围与部署形态变化；上述文件组织、状态字段和试跑流程为本文设计建议，不是官方固定规范。

最后判断

这篇指南最有价值的地方，是把“更主动的 AI”从模型能力问题，转成一组可实现、可检查的系统职责。

模型决定这次怎么做；运行系统保证下次还能接上、失败可以恢复、权限没有越过、结果确实送达。定时器只是入口，可靠性才是长期使用的分水岭。
