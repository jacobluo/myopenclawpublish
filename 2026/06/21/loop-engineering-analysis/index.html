Loop Engineering：从提示词走向可运营的 Agent 循环

Loop engineering 是 AI 编程代理从“人驱动的一次次 prompt”走向“系统驱动的持续工作流”的工程化阶段。它把发现任务、分派执行、验证结果、记录状态、升级给人这些动作设计成可重复、可审计、可暂停的循环。

1 层更高位于 harness 之上
5+1调度、worktree、skills、connector、subagent、memory
L1 先行报告型循环优先于自动修改
人仍负责判断、验收、边界与风险

一句话判断

  • Prompt engineering 优化单次对话。
  • Harness engineering 优化单次 agent run 的运行环境。
  • Loop engineering 优化跨时间、跨任务、跨多次运行的工作系统。
  • 真正的价值不是“无人值守”，而是把重复监督变成可度量的系统。

执行摘要

Loop engineering 的核心不是“让 agent 自己干活”，而是“设计一个能反复唤起 agent、约束 agent、检查 agent、并把进度写回外部状态的控制系统”。

它的出现是 AI 编程代理成熟后的自然结果：当 Claude Code、Codex、Cursor、Grok 等工具已经具备调度、技能、连接器、工作区隔离和多代理能力后，工程师的杠杆点从“如何写一个好 prompt”转向“如何设计一个可持续运行的闭环”。Addy Osmani 把它概括为：不要再做那个不断提示 agent 的人，而是设计替你提示 agent 的系统。

这不是一个全新的框架，而是一种系统设计范式。成熟的 loop 不应该一开始就自动改代码、自动合并、自动发布。正确路线是从 L1 report-only 开始，让 loop 先负责发现、整理、记录和提醒；等它的信号质量稳定后，再逐步开放小范围动作，例如修复格式、补测试、处理依赖补丁或起草 PR。

概念定义

Loop engineering 可以定义为：为 AI agent 设计一个可重复运行的外部控制循环，使它能够按固定或事件驱动的节奏发现任务、读取上下文、调用技能、分派子代理、隔离执行、验证结果、更新状态，并在不确定或高风险时交还给人。

发现定时或事件触发，扫描 CI、PR、issue、数据源、日志。 归类调用 triage skill，把信号分成噪音、建议、待行动。 分派为可行动项开 worktree，交给实现 agent 或专门技能。 验证由独立 checker 运行测试、审查 diff、判断是否满足停止条件。 记录把尝试、结果、失败原因和下次动作写入外部 state。 升级遇到高风险、歧义或多次失败时，带上下文交给人。

这套流程里最关键的不是“循环”两个字，而是循环外部的工程约束：状态文件、预算、权限、停止条件、回滚路径、观察指标和人类交接规则。没有这些，loop 只是一个会重复犯错的 cron prompt。

为什么现在流行

1. 工具原语成熟

调度、skills、MCP connector、subagent、worktree 这些能力已经从自建脚本变成主流 agent 工具的内置能力。Codex automations 可以定时运行并进入 triage；skills 可以把可复用工作流封装成可触发知识包；subagents 可以并行探索或承担 maker/checker 分工。

2. 单次 prompt 的边际收益下降

复杂工程任务的问题不再只是“模型听不懂”，而是它需要跨多个运行窗口保持上下文、处理失败、避免重复劳动、控制成本和知道什么时候停。单次 prompt 很难承担这些运营职责。

3. 长任务暴露记忆断层

Anthropic 的长运行 agent 文章指出，多窗口任务会遇到“每个新 session 都像新人接班”的问题。Loop 的 state/memory 机制就是为了解决跨运行交接。

4. 团队开始关心运营指标

当 agent 从玩具变成团队工具，问题从“能不能生成代码”变成“能否降低响应时间、减少人类扫尾、稳定处理重复流程”。这天然需要 loop 而不是聊天。

Loop Engineering 与 Harness Engineering 的区别

最简单的区分：harness 是 agent 一次运行时的“装备和跑道”；loop 是让多次运行形成持续工作的“运营系统”。

维度 Harness Engineering Loop Engineering
关注层级 单个 agent run 的上下文、工具、沙箱、提示、hook、观察性。 跨运行、跨时间、跨任务的发现、分派、验证、记忆和升级。
核心问题 “怎样让这个 agent 在这次任务中不迷路、不误操作？” “怎样让系统每天/每小时自己发现该做什么，并可靠推进？”
典型产物 AGENTS.md、skill、工具描述、沙箱规则、hook、测试命令。 STATE.md、调度器、run log、budget、watchlist、handoff inbox。
失败模式 工具太危险、上下文不够、prompt 不清、验证缺失。 重复修错、状态漂移、通知疲劳、成本失控、无人确认却自动行动。
工程比喻 给工人配工具、护具、说明书和验收标准。 设计班次、工单流、质检、交接记录和升级机制。

关系不是替代，而是包含。 一个可靠 loop 必须建立在可靠 harness 之上。没有 harness，loop 只是把不可靠行为重复更多次；没有 loop，harness 只能提升单次 agent 工作质量，无法形成持续运营。

工程实践：如何设计一个能用的 Loop

1. 从 report-only 开始

第一个 loop 不要自动改代码。最稳妥的起点是 Daily Triage：每天或每 2 小时读取 CI、issue、PR、近期 commit、项目状态，输出一份优先级清单，写入 STATE.md 或 Linear/GitHub Project。运行一周后，对比它与人工判断的差异，再决定是否放开行动权限。

2. 把任务写成 skill，而不是写成长 prompt

Loop 的 prompt 应该短，真正的项目规则放在 skill 里。比如 loop-triage 负责“如何读 CI、如何判定优先级、输出格式是什么”；minimal-fix 负责“小修复的边界”；release-note-drafter 负责“如何从 merged PR 生成 changelog”。这样 loop 可维护，也便于复用。

3. 任何会写文件的 loop 都应使用 worktree

并行 agent 最常见的灾难是互相覆盖文件。worktree 把不同 agent 的改动隔离在不同 checkout 里，降低冲突与误操作。它不是银弹，仍需要人审查 diff，但它让并行探索从机械上可控。

4. Maker 与 Checker 必须分离

写代码的 agent 不应该给自己判定“已完成”。至少需要一个独立 verifier：检查 diff 是否只改了目标范围、测试是否真的跑过、有没有安全/权限/依赖风险。高风险任务还要把 verifier 放在更强模型或更高 reasoning effort 上。

5. 状态文件是 loop 的脊柱

一个 loop 必须在每次运行开始读状态、结束写状态。最低限度需要记录：上次运行时间、发现项、行动项、尝试次数、失败原因、等待人类决策的事项、已关闭事项。没有外部 state，loop 会在每次运行时失忆。

6. 预算和停止条件要写进系统

高频 loop 很容易烧 token。PR babysitter 或 CI sweeper 每 5 分钟跑一次，如果没有 early exit、预算上限和最大尝试次数，会迅速变成成本黑洞。每个 loop 都应有 loop-budget.md、loop-run-log.md 和 kill switch。

工程价值

响应速度

更快发现问题

CI 红了、PR 卡住、issue 噪音增加时，不再等人主动巡检。Loop 把发现问题的延迟从“人什么时候想起来看”降到固定 cadence。

质量控制

让验证成为流程

成熟 loop 会强制 maker/checker 分离，减少 agent 自我感觉良好导致的假完成。

组织记忆

沉淀决策和上下文

状态文件、run log、skills 把隐性经验变成可读资产，减少重复解释和重复犯错。

并行能力

安全扩大吞吐

worktree + subagent 让探索、实现、验证可以并行，但仍受人类 review 带宽约束。

运营化

从助手变成后台流程

Agent 不再只是“问一下”，而是可以成为团队工程系统中的 watcher、triager、drafter、sweeper。

治理

降低黑箱自动化风险

好的 loop 把权限、记录、升级和停止条件显式化，让自动化行为能被审计。

风险与反模式

最危险的误解：把 loop engineering 理解成“让 AI 完全替我工作”。正确理解是：让系统承担重复运营动作，让人类保留判断、边界、验收和责任。

反模式 表现 治理方式
Prompt cron 只把长 prompt 放进定时器，没有 state、预算、验证。 补齐 state、run log、skill、early exit。
自我验收 同一个 agent 写代码并宣布完成。 独立 verifier；必要时更强模型或人工 gate。
无限修复循环 同一个 PR/CI 失败被反复修改，越修越乱。 最大尝试次数；三次失败自动升级给人。
通知疲劳 每次运行都 ping 人，导致人忽略真正信号。 只在需要决策、超预算或高风险时通知。
理解债务 loop 产出越来越多，人越来越不理解系统。 定期读 diff、写决策记录、限制自动改动范围。

实践建议：如何开始

建议按四级成熟度推进，不要跳级。

阶段 目标 允许动作 退出条件
L0 草案 定义 loop 目的、范围、非目标。 只写设计文档。 有明确 owner、cadence、数据源、状态格式。
L1 报告型 自动发现和整理信号。 写报告、更新 state，不改业务代码。 连续一周信号质量稳定，噪音可控。
L2 协助型 处理低风险小动作。 开 worktree、起草 PR、补测试、修格式。 验证通过率高，人工返工率低。
L3 半无人值守 在 allowlist 内持续运行。 有限自动提交、自动评论、自动关单。 有预算、日志、审计、回滚和 kill switch。

推荐的第一个 loop

如果团队还没有 loop 经验，首选 Daily Triage Loop：每天早上扫描 GitHub issues、PR、CI、近期 commit 和项目状态，写一份 STATE.md。它风险低、回报快、容易评估，也能训练团队如何维护 state 和 skill。

适合 OpenClaw / 个人工作流的三个候选

研究报告 loop

每天/每周从指定来源发现高价值话题，生成候选清单；人选题后再深研。适合现在的 Follow 日报和专题报告。

项目维护 loop

定时检查 Pages 发布、数据抓取、脚本失败、仓库状态，自动写状态文件，只在异常时提醒。

链接深读 loop

当你丢博客、GitHub 仓库或技术链接时，自动识别对象类型，选择对应分析模板，沉淀引用和反方观点。

一份可直接用的 loop 设计模板

Loop 名称：Daily Research Triage

目的：每天发现 5 个值得深研的 AI engineering / agent engineering 信号。

输入：RSS、GitHub trending、指定作者博客、X/Follow 列表、已有 memory。

输出：STATE.md 中的候选主题、证据链接、优先级、建议动作。

权限：L1 阶段只写报告，不自动发布；发布必须由人确认。

升级条件：来源冲突、重大事实不确定、涉及投资建议或成本较高时交给人。

成功指标：人类采用率、低噪音率、报告返工率、遗漏重要事件次数。
