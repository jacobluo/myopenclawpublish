Why Now

AI 的 Demo 很容易，生产落地很难

  • 模型能力快速提升，但企业工作流吸收速度慢。
  • Agent 要接数据、工具、权限、审批和业务规则。
  • 失败常常不在模型，而在部署现场。
  • FDE 重新变热，是因为它填补了从能力到落地的断层。

Definition

FDE 是什么？

FDE 是嵌入客户现场的工程师，负责把模糊业务问题变成可运行的生产系统，并把现场学习反哺给产品。

靠近现场

理解真实工作流、隐性规则、组织约束和用户习惯。

拥有代码

不只是建议方案，而是做集成、写工具、交付系统。

反哺产品

把反复出现的问题沉淀成 evals、playbooks 和产品能力。

角色定义 3 / 14
Not Consulting

FDE 不是“高级实施顾问”

  • 顾问交付项目，FDE 交付系统和产品学习。
  • 解决方案工程师证明价值，FDE 承担生产落地。
  • 客户成功推动采用，FDE 用工程手段移除阻塞。
  • FDE 的关键产出不是定制工作本身，而是可复用能力。
顾问 客户侧、建议/交付
产品工程师 产品侧、代码拥有
客户成功 客户侧、采用推动
FDE 客户侧 + 产品侧，代码拥有 + 反馈闭环

Origin

源头：Palantir 的 FDSE 模型

复杂、高价值、非标准化的问题，不能只靠远程产品路线图解决。

Agent Era

为什么 AI Agent 让 FDE 更重要？

  • Agent 需要吸收未写下来的业务判断。
  • 边界条件、例外流程和审批权限决定能否自动化。
  • RAG、工具调用、权限和日志常常比 prompt 更关键。
  • FDE 负责发现 Agent 真正需要知道什么、能做什么。

水面上

模型、Prompt、聊天界面、Demo

水面下

数据质量、系统权限、用户激励、异常流程、合规要求、人工审批、组织责任

闭环模型 7 / 14
Product Compression

FDE 把现场混乱压缩成产品资产

变成 evals 和回归测试，防止下次再错。

When To Use

什么场景值得投入 FDE？

适合

  • 高价值企业客户
  • 复杂数据和权限环境
  • AI Agent 进入核心工作流
  • 边界条件多、隐性知识多
  • 需要从现场提炼产品能力

不适合

  • 简单自助型 SaaS
  • 低客单、低复杂度业务
  • 纯人力实施，无法产品化
  • FDE 被当成售后或临时救火
  • 没有 evals 和反馈吸收机制
适用边界 11 / 14
Operating Model

FDE 团队应该怎么放？

靠近客户

小团队嵌入战略客户，直接面对真实业务流程和上线指标。

连接产品

每周回看现场失败、重复需求、eval 缺口和路线图信号。

沉淀资产

把脚本、规则、工具和经验变成共享仓库和标准 playbook。

FDE 不应被埋在服务部门里，而要直接连接产品和工程。

组织设计 12 / 14
Risks

最大的风险：FDE 变成昂贵定制服务

  • 每个客户都变成独立项目。
  • 现场学习没有进入产品路线图。
  • 只考核交付量，不考核产品杠杆。
  • 没有 evals、没有 playbooks、没有复用组件。
  • 销售承诺超过产品真实能力。

诊断问题

如果同一个现场问题每个季度都重复出现，说明产品没有吸收 FDE 的学习。
